# Spec — Observabilidade: erros/perf, eventos do bot, custo de LLM (Fase 9)

- Domínio: observabilidade (**domínio novo** — transversal: API, worker, bot, web, `modules/ai`; sugere entrada nova em `ia-docs/domain/context-map.md`) | Data: 2026-10-09 | Status: rascunho
- **Decisões do humano (2026-10-09, aplicadas nesta spec)**: Aberto #1 = **GlitchTip SaaS** (free, tier 5k eventos/mês — compatível com o SDK do Sentry; DSN trocável); #2 = **reter `bot_events` para sempre**; #3 = **reter `llm_calls` para sempre**; #4 = **custo de LLM só admin** (confirmado); #5 = **(revertida no mesmo dia) tracker NÃO é anônimo, mas é da assimetria admin/cliente**: event leva **somente `userId`** para o admin filtrar erros por conta no painel; e-mail/telegramId **nunca** vão ao tracker — quem precisa de identidade crua é o **admin cruzando `userId` no Postgres**; o **cliente nunca acessa o tracker** (vê apenas os próprios eventos via `/bot-events`, B5); #6 = **rollout por flag no user** (`observabilidadeEventosAtivo`, admin liga por usuário); #7 = **tracing OFF** até produção real (ligar é env).

Registrar antes de codar.
- Pedida por: usuário (Fase 9 — "Última etapa — Observabilidade", PROMPT.md ~linha 150) | Fase do roadmap: **9 (última)**
- Estado acoplado (verificado por inspeção 2026-10-09, não re-descrito): **zero** error tracker hoje (nenhum `Sentry`/OTel no repo). Env da API **já é validada por zod no boot** (`apps/api/src/config/env.validation.ts` + `validateEnv`, o processo morre cedo) — é a borda onde as variáveis novas entram. O worker é processo próprio (`workers/notifications-worker.ts`, ADR-009). O bot mora em `modules/bot` (`bot-gateway.service.ts` só loga erro com `Logger` do Nest; a máquina de estados em `scheduling-flow.machine.ts` conhece etapa e decisão; intenção vem de `modules/ai/intent-classifier.service.ts` — ADR-008). As 5 saídas de LLM (`intent/scheduling/consulta/edit/reminder-interpreter`) passam **todas** por `AnthropicMessagesClient` (interface mínima em `ai/anthropic-messages-client.ts`); **o resultado hoje descarta `usage`** (tokens) — a interface não o expõe. O Prisma tem 6 models, nenhuma tabela de eventos/custo. Web: env em `app/config/env.ts` (`import.meta.env`), TanStack Query, padrão AuthHandoff (nenhum dado em query param).

## Objetivo / dor do usuário

Hoje, quando algo quebra, não há para onde olhar: erro na API/worker/web desaparece no stderr; uma conversa do bot que terminou errada é invisível (não dá para saber que intenção o LLM viu, em que etapa a máquina travou ou por que um compromisso caiu em **revisão**); e ninguém sabe quanto o LLM custa nem por quem. Esta fase entrega as três peças do PROMPT 9: **(1)** erros/performance da plataforma num tracker (Sentry ou similar) com PII scrubbed; **(2)** **registro estruturado e consultável por usuário de cada interação do bot** (quem/o que/quando/resultado); **(3)** tokens e custo estimado por chamada de LLM, agregável por usuário e período. É telemetria sobre o comportamento existente — **nenhuma regra de negócio nova, nenhuma decisão movida de lugar**.

## Comportamento esperado

### A. Erros e performance da plataforma (GlitchTip SaaS via SDK Sentry — API, worker, web)

A0. **Tracker escolhido (humano 2026-10-09): GlitchTip SaaS**, tier grátis (~5.000 eventos/mês, usuários ilimitados). Os SDKs `@sentry/*` são **compatíveis por protocolo** com o GlitchTip: o código usa o SDK do Sentry e o `SENTRY_DSN` aponta para o GlitchTip; trocar de fornecedor (inclusive Sentry SaaS ou self-hosted) é **trocar o DSN**, zero mudança de código (vai para o ADR-0016).

A1. **Um init por processo, DSN opcional**: `@sentry/nestjs` na API (`main.ts`, antes do `listen`), `@sentry/node` no entrypoint do worker e do processo do bot (`dev:bot` é processo próprio — ADR-009), `@sentry/vite-plugin` + browser SDK na web. **`SENTRY_DSN` ausente ⇒ o processo liga normalmente sem tracker** (mesma flexibilidade de `TELEGRAM_BOT_TOKEN`/`ANTHROPIC_API_KEY` em `env.validation.ts`) — testes e dev não dependem de rede. Variáveis novas entram **no zod de `env.validation.ts`** (padrão de env já existente): `SENTRY_DSN?` (no deploy, aponta para o projeto do GlitchTip), `SENTRY_TRACES_SAMPLE_RATE` (default `0`), `SENTRY_ENVIRONMENT` (default = `NODE_ENV`).
A2. **Environment/release em toda event**: `environment`, `release` (versão do package + `dist`/commit quando disponível) e **tag `process: api | worker | bot | web`** — sem a tag, não se diferencia o erro do worker do erro da API no painel.
A3. **Scrub de PII é invariante de entrega** (o PROMPT pede "sem dados pessoais na stack"): `sendDefaultPii: false`; `beforeSend` derruba **corpo de request, cookies, authorization, headers de auth** e qualquer `email`/`telegramId`/`fala` que apareça em extra/breadcrumb (a identidade permitida é só `userId` — A5); no browser, **nenhum dado de compromisso no breadcrumb** (URL da web só com o **path**, sem query — reforço do padrão AuthHandoff) e nenhum `captureException` com payload de agenda. O **bot** nunca reporta a _fala do usuário_ como mensagem/extra — só `userId`, identificadores opacos (A5) e nomes de etapa/intenção.
A4. **Performance**: tracing habilitado por `SENTRY_TRACES_SAMPLE_RATE` (default **0** = desligado; ligar é decisão operacional). HTTP middleware na API; jobs do worker instrumentados como span próprio (nome da fila + `kind` reminder/digest, **sem** payload). Performance da web: o browser SDK padrão (page load + HTTP spans) cobre o pedido; web-vitals dedicado é fora de escopo.
A5. **Assimetria admin/cliente (D5 — decisão humana 2026-10-09, substitui "anônimo")**: a event leva **somente `userId`** (id interno opaco do Postgres, via `setUser`/scope quando a requisição/turno tem usuário autenticado) para o **admin** filtrar/agrupar erros por conta no painel. **E-mail e `telegramId` nunca vão ao tracker** — nem crus, nem hasheados: quem precisa de identidade cruza o `userId` no Postgres (ferramenta do admin). O **cliente/usuário final nunca acessa o tracker**; a visão dele é `/bot-events` com os próprios eventos (B5). Justificativa registrada no ADR-0016: `userId` atende o pedido de detalhe do admin sem dar dado pessoal a um SaaS externo e sem contradizer o requisito do PROMPT ("sem dados pessoais na stack" = conteúdo: fala, e-mail, títulos/notas); reversível por config só com decisão humana nova.

### B. Eventos do bot por usuário (registro estruturado consultável)

B1. **Nova tabela `bot_events` no Postgres** (alternativa log-JSON rejeitada — D2; "consultável por usuário" pede query, agregação e UI sem infra de logs): `id`, `userId` (FK `onDelete: Cascade` — regra de escrita de conta existente), `telegramId` **ofuscado** (`telegramIdHash` = sha256 truncado com salt de `JWT_SECRET`; coluna crua **não entra** — D6), `type` (enum Prisma, D7), `stage` (texto livre controlado: etapa da máquina/intenção/result — **não** enum no banco para não migrar a cada fala), `outcome` (enum: `ok | needs_review | conflict | error | aborted`), `metadata` (jsonb, zod-gated em `contracts`, **sem PII livre**: nada de fala do usuário, título ou notas — D8), `createdAt` UTC (ADR-002). Índices: `(userId, createdAt)`, `(type, createdAt)` — e todo índice/FK declarado explicitamente (lição do review/gotcha 21).
B2. **Tipos cobertos** (derivados do fluxo existente, zero comportamento novo): turno recebido (sem o texto), `intent` classificada (ADR-008: valor + faixa de confiança), transição relevante da máquina (etapa a→b), **decisão de regra** (conflito sim/não — vem de `schedule-core`/API, o evento só _registra_), resultado (criou / editou / cancelou / needs_review / abortou), resposta de conflito no chat (mostrada/aceita/recusada).
B3. **Onde mora**: serviço `BotEventsService` em **`modules/observabilidade`** (módulo novo; o bot/handlers **não** montam evento — handler só chama `registrar(...)`; regra `default-architecture.md`: zero lógica no handler). **`schedule-core` permanece puro** (telemetria é I/O — `schedule-core.md` é explícito).
B4. **Best-effort nunca silencioso**: gravação de evento **não pode** derrubar o turno nem travar a conversa — `Promise` com `.catch` que loga via `Logger` (e Sentry, se ativo). Falha de telemetria ≠ falha do produto. Eventos **nunca** são gravados dentro de transação Prisma de negócio (padrão do repo: efeitos colaterais pós-commit).
B5. **Consulta (decidido 2026-10-09 — rollout por flag)**: `GET /bot-events?userId=&from=&to=&type=` (auth'd, zod — `contracts/api`), paginação simples `limit/offset`. **Admin** (flag `isAdmin` do user — ver B6): vê tudo, filtro `userId` opcional. **Usuário comum**: vê SOMENTE os próprios eventos (filtro `userId` do token, ignorando o parâmetro da query) **se e somente se** `user.observabilidadeEventosAtivo === true` — caso contrário 403 sem vazar existência. Flag **default `false`** para todo mundo; novos usuários nascem fora do rollout. Web: **nenhuma tela nova nesta fase** (fora de escopo) — a consulta é por API; UI de auditoria fica devendo.

B6. **Papel de admin + flag de rollout (novo — nasce da decisão do Aberto #6)**: **migration única** também adiciona em `users`: `isAdmin Boolean @default(false)` e `observabilidadeEventosAtivo Boolean @default(false)`. O **primeiro usuário cadastrado** do sistema vira `isAdmin = true` automaticamente no signup (regra declarada e testada; quando existir multi-admin, um ADR novo muda isso — nesta fase admin único implícito). O admin gerencia o rollout por `PATCH /admin/users/:id/observabilidade` (`{ observabilidadeEventosAtivo: boolean }`, auth'd + admin-only + zod; resposta = o user atualizado). A flag **só libera o rollout de eventos do bot** — nada mais é condicionado a ela.

### C. Tokens e custo do LLM por usuário

C1. **Nova tabela `llm_calls`** (alternativa "colunas na tabela existente" não existe — não há tabela de chamadas — e "log JSON" quebra o "agregável" do PROMPT, D3): `id`, `userId` (FK, nullable — chamada sem usuário conhecido é `null`, nunca chute), `purpose` enum (`intent | criar_extracao | consulta | edicao | lembrete_atalho` — espelha os 5 services de `modules/ai`; **`escalada` vira flag** `escalated` + `modelUsed`, não purpose), `modelUsed`, `inputTokens`, `outputTokens`, `costUsdMicros` (inteiro: **custo estimado em micro-USD** — float somado em SQL é armadilha), `latencyMs`, `outcome` (`ok | parse_fail | low_confidence | escalated | error`), `createdAt` UTC + índices `(userId, createdAt)`, `(createdAt)`.
C2. **Capture centralizado no `anthropic-client.provider.ts`** (único ponto por onde as 5 saídas de LLM passam): a interface `MessagesCreateResult` ganha `usage?: { input_tokens; output_tokens }` (o SDK já devolve) e o provider emite o registro. **Nenhum service de IA muda de comportamento** nem conhece custo; os stubs de teste existentes continuam válidos (`usage` ausente ⇒ `inputTokens/outputTokens` null, linha ainda gravada com `outcome`).
C3. **Custo é estimativa declarada**: preço por MTok entra por env (`LLM_PRICE_IN_PER_MTOK`, `LLM_PRICE_OUT_PER_MTOK`, defaults **numéricos** alinhados ao ADR-008 — primário $1/$5, escalada $2/$10 — preço por modelo mapeado no service de custo, fonte: planilha do pricing do modelo, documentada no comentário). O campo se chama `costUsdMicros` **porque é estimativa**, não billing da Anthropic.
C4. **Agregação**: `GET /llm-usage?from=&to=&groupBy=user|purpose` (auth'd, **admin-only** — humano 2026-10-09: custo NUNCA é exposto ao usuário final, rollout nenhum o libera; zod) → soma de tokens, custo total estimado e contagem de chamadas por usuário/período — o "gasto total" do PROMPT. A tabela crua **não** tem dado pessoal além do `userId` (sem `rawText`, sem fala) — custo por usuário é atribuição interna, não exposição.
C5. **Retenção (decidido 2026-10-09)**: `bot_events` e `llm_calls` retidas **para sempre** — sem job de expurgo nesta fase (reavaliar se doer o volume; a decisão vive no ADR-0017).

### D. Transversal / invariantes

D-T1. **Nada muda no comportamento visível** do bot/web/worker: nenhuma fala, tela ou decisão muda (`docs/cenarios-do-bot.md` intocado — regra `documentation.md` 8). `schedule-core` intocado. Nenhuma lógica de negócio em controller/handler; evento é _consequência_ observada, nunca insumo de decisão (telemetria não alimenta regra — proibido).
D-T2. **zod em toda borda**: envs novas em `env.validation.ts` (API/worker/bot), `metadata`/`stage`/queries de listagem em `contracts`, env da web via `app/config/env.ts` (`VITE_SENTRY_DSN?` — DSN de browser é publicamente visível por natureza, mas **não** é segredo e **não** vai para código).
D-T3. **Privacidade como invariante das três peças**: tracker com **`userId` apenas** — zero conteúdo pessoal, zero e-mail/telegramId, nem hasheados (A3/A5); `bot_events` sem fala/título/nota e com `telegramId` só ofuscado (B1/D6); `llm_calls` sem conteúdo (C1). **Nenhuma query de telemetria usa dado em query param** além de filtros técnicos (`from/to/type`) — padrão do repo; o `userId` da consulta de eventos **não é parâmetro do cliente comum** (vem do token).
D-T4. **Decisões não-óbvias viram ADR** (PROMPT 9): ADR-0016 (ferramenta/scrub) e ADR-0017 (on-disk vs log, retenção) registrados antes de codar.

## Critérios de aceite (Gherkin)

### Sentry SDK → GlitchTip (verificação por smoke semeado + teste de `beforeSend`)

- **Dado** `SENTRY_DSN` **ausente** no ambiente **Quando** API, worker ou web iniciam **Então** os três sobem e passam nos gates **sem** tentativa de rede ao tracker (teste: init é no-op).
- **Dado** `SENTRY_DSN` apontando para um endpoint local de teste (mock HTTP — o GlitchTip SaaS real só entra no smoke final com projeto de teste) **Quando** um erro é semeado **em cada processo** (API: rota que lança; worker: job que joga; bot: handler com exceção semeada em teste; web: `captureException` disparado no console do smoke) **Então** 4 events chegam com `environment`, `release` e `tags.process` distintos (`api`/`worker`/`bot`/`web`).
- **Dado** um request à API que explode **com corpo contendo e-mail do usuário e header Authorization** **Então** a event enviada **não contém** o e-mail, o header nem o corpo (teste de unidade do `beforeSend` com JSON-seed — asserta que a string do e-mail não aparece no payload serializado).
- **Dado** um turno do bot que gera erro no handler **Então** a event **não contém a fala do usuário** nem título/nota de compromisso; **e** contém `user.id = userId` quando o turno tem usuário autenticado (teste: seed com userId asserta `event.user.id` presente e as strings de e-mail/telegramId ausentes).
- **Dado** uma event de contexto autenticado **Então** ela **não contém e-mail nem telegramId** — crus ou hasheados — em `user`, `extra` ou breadcrumb (o `beforeSend`_strip mesmo que o caller tente anexar; teste de unidade).
- **Dado** `SENTRY_TRACES_SAMPLE_RATE=0` (default — humano 2026-10-09: tracing só na produção) **Então** nenhuma transação/span é enviada (só errors).

### Eventos do bot (jest do service + e2e)

- **Dado** usuário confirmado **Quando** marca um compromisso no bot (fluxo completo: intenção `criar` → etapas → criação) **Então** `bot_events` tem ao menos: 1 linha de turno, 1 de intent (`metadata` com intent + faixa de confiança, **sem** o texto da fala), N de transição de etapa, 1 `resultado` com `outcome: ok` — todas com `userId` certo e `createdAt` UTC.
- **Dado** um turno que cai em **revisão** (confiança baixa) **Então** existe linha com `outcome: needs_review` **E** nenhuma linha contém o texto da fala do usuário em `metadata` (teste e2e asserta `rawText`-like ausente).
- **Dado** conflito confirmado no chat (o bot re-pergunta e o usuário aborta) **Então** linha `outcome: conflict` e linha final `outcome: aborted`, **sem** título do compromisso conflitante no evento.
- **Dado** o Postgres fora do ar para o `BotEventsService` (mock rejeita) **Quando** o usuário conversa **Então** a resposta do bot é idêntica ao comportamento atual e o erro é logado localmente (teste: a exceção do registro não propaga).
- **Dado** `GET /bot-events?userId=&from=&to=` **sem** token **Então** 401; **Dado** usuário comum **não liberado** (`observabilidadeEventosAtivo=false`) pedindo os próprios eventos **ou** os de outro usuário **Então** 403 (sem vazar existência); **Dado** usuário comum **liberado** pelo admin **Então** 200 **somente com os eventos dele** — o filtro `userId` da query é ignorado para não-admin; **Dado** admin **Então** 200 paginado ordenado por `createdAt` desc, com `userId` opcional.
- **Dado** primeiro cadastro num sistema com `users.isAdmin=false` para todos (novo banco) **Então** esse usuário nasce `isAdmin=true`; o segundo nasce `isAdmin=false` (regra D12 testada).
- **Dado** `PATCH /admin/users/:id/observabilidade` **Então** só admin altera `observabilidadeEventosAtivo` (200 com o user atualizado); não-admin 403; nada mais no user é alterável pela rota.
- **Então** `telegramId` cru **não existe** em `bot_events` (schema inspecionado) e o hash é determinístico para o mesmo id, não colando com busca por e-mail (teste de unidade).

### Custo de LLM (jest do provider + service, com stub)

- **Dado** uma chamada de extração cujo stub retorna `usage: { input_tokens: 100, output_tokens: 20 }` no modelo primário **Quando** a chamada termina **Então** uma linha `llm_calls` com `purpose: criar_extracao`, tokens exatos, `costUsdMicros = 100·preço_in + 20·preço_out` em micro-USD (assertar o inteiro exato — regra de arredondamento: inteira mais próxima, documentada no service), `userId` do dono da conversa.
- **Dado** o stub **sem** `usage` (client antigo/mock existente) **Então** a linha é gravada com tokens `null` e `costUsdMicros` `null` **E** o comportamento do service de IA é idêntico (nenhum teste existente dos interpreters quebra).
- **Dado** parse falho do zod na resposta **Então** `outcome: parse_fail` **E** (se houver escalada) `escalated: true` com `modelUsed` do modelo de escalada — o custo da tentativa falha **também** é registrado (gasto é gasto).
- **Dado** erro de rede do Anthropic **Então** `outcome: error` com latência e `userId`; nenhuma linha dupla para a mesma tentativa (1 linha por chamada `messages.create`, incluindo retentativas = N linhas).
- **Dado** `GET /llm-usage?from=&to=&groupBy=user` **Então** soma de `costUsdMicros` por usuário bate com o somatório manual das linhas do período (teste e2e semeando 3 chamadas de 2 usuários).

### Gates

- **Então** `pnpm build && pnpm test && pnpm lint && lint:arch` verdes (módulo `observabilidade` respeita depcruise — bot→observabilidade permitido, observabilidade→bot **proibido**: o serviço não importa o gateway);
- **Então** nenhum `console.log`/`Logger` novo solto fora do padrão, nenhum dado pessoal em Sentry/eventos (testes de scrub acima são o gate), e `schedule-core` sem diff.
